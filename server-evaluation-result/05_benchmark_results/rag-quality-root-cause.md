# RAG 기준선 품질 원인 분석

이 문서는 원시 418 run을 폐기하거나 점수를 임의로 올리지 않고, 낮은 기준선이
`평가 입력 결함`, `채점 규칙`, `실제 RAG 결함` 중 어디에서 발생했는지 분리한
진단 기록이다. 원시 기준선 43.30%는 그대로 보존한다.

## 1. 동일 원시 run의 평가 가능 범위 재분류

| 범위 | run | 정답 | 정확도 | 해석 |
| --- | ---: | ---: | ---: | --- |
| 원시 전체 | 418 | 181 | 43.30% | 기존 보고값, 오류·모호 질문 포함 |
| 기업이 명시되고 catalog에 존재하며 gold를 파싱할 수 있는 질문 | 322 | 168 | 52.17% | 현재 제품이 실제로 답할 수 있는 범위 |
| 위 조건 중 원본 셀 직접 조회형 | 210 | 138 | 65.71% | 검색·Reader의 가장 신뢰도 높은 기준선 |
| 위 조건 중 계산·판단형 | 112 | 30 | 26.79% | 계산 결과와 보조 수치를 모두 강제하는 기존 scorer 영향이 큼 |

범위 제외 사유는 중복될 수 있다. 418 run 중 기업명이 질문에 명시되지 않은
run이 76개, 현재 catalog 밖 기업 질문이 6개, 원본 reference를 자동 파싱하지
못한 run이 26개였다. 이 조건을 모두 적용하면 평가 가능한 run은 322개다.

## 2. 평가 입력·gold 결함

### 기업 스코프가 질문에 없음

1차 질문 중 기대 기업은 IBM이지만 질문에는 기업명이 없는 사례가 존재한다.
예를 들어 `F1-Q004`는 “2024-12-31 기준 희석 EPS와 DPS는?”만 전달한다. 독립
실행에서 어느 기업인지 알 방법이 없으므로 catalog 안의 다른 기업을 고르거나
안전하게 중단한 결과를 IBM 오답으로 채점해서는 안 된다.

개선 기준은 모든 독립 평가 질문에 기업명을 명시하는 것이다. 대화 문맥을
평가하려면 이전 턴을 별도 입력 필드로 제공해야 한다.

### catalog 밖 기업을 정상 답변 대상으로 채점

`F1-Q013`~`F1-Q015`는 Bank of America/BAC 질문이지만 평가 시점 catalog에는
해당 기업 workbook이 없었다. Decomposer의 거부는 안전 동작이다. 이 사례는
`expected_abstain=true`로 채점하거나 해당 workbook을 적재한 별도 평가로
분리한다.

### 질문이 요구하지 않은 부가 계산값 강제

`F1-Q001`은 시가총액과 TEV를 각각 묻는다. 두 workflow 모두 정답 셀 `E60`,
`E69`를 인용하고 두 값을 정확히 답했지만, gold의 선택적 설명값인 차이
`50,283`까지 `expected_numbers`에 들어가 오답 처리됐다. 기존 `_score`는 모든
숫자를 필수로 간주한다.

향후 gold는 질문에 직접 요구된 `required_numbers`와 설명에만 필요한
`supporting_numbers`를 분리한다. 원시 결과의 점수는 소급 변경하지 않는다.

### 유효한 대체 시트를 오답으로 간주

같은 지표가 `Key_Stats`와 재무제표에 모두 존재할 수 있다. `F2A-O1-12`는
Key_Stats의 유효 셀로 세율을 정확히 답했지만 기대 시트가
`Income_Statement` 하나여서 route/sheet 오답이 됐다. Sheet exact는 검색
효율 진단값으로 보존하되 Answer 정확도와 별도로 해석한다.

### 질문 용어와 원본 FEATURE가 불일치

원본 209문항을 실제 workbook의 행 label·FEATURE code와 대조한 결과, 25문항은
`매출` 계열 질문이 `Total Revenue` 셀을 정답으로 가리키는 등 질문과 gold의
의미가 일치하지 않았다. 이 경우 `Revenue`를 찾은 시스템이 오답이고
`Total Revenue`를 찾은 시스템이 정답이라는 결론을 낼 수 없다.

정제 규칙은 `총매출/총매출액 = Total Revenue`, `매출/매출액 = Revenue`다.
총부채(`Total Liabilities`)와 총차입금(`Total Debt`)도 같은 방식으로
구분한다. 평가셋 오류를 맞히기 위해 제품의 의미 규칙을 왜곡하지 않는다.

또한 기업 범위 생략 31건, 암묵적 기업 그룹 3건, catalog 밖 기업 3건,
현재 적재하지 않는 시트 관련 5건을 확인했다. 전수검사 결과와 209개 수정
질문 전체 목록은 `evaluation-set-quality-review.md`에 기록했다.

## 3. 실제 RAG 결함

직접 조회형 유효 run 210개 중 실패 72개를 단계별로 분해했다. 아래 건수는 한
run이 여러 원인에 해당할 수 있어 합계가 72를 초과한다.

| 원인 | 실패 run | 판단 |
| --- | ---: | --- |
| 실행 또는 기업 스코프 실패 | 24 | catalog에 IBM이 있는데 모델의 `unresolved_companies`를 그대로 신뢰한 결함 |
| 기대 근거 셀 미회수 | 47 | 행 의미·기간·시트 선택 또는 retrieval miss |
| strict sheet 불일치 | 54 | 실제 오답과 유효 대체 시트가 혼재 |
| route와 근거는 도착했지만 답변 오답 | 18 | Reader 완전성·계산 또는 scorer/gold 문제 |
| gold 근거와 인용이 모두 완전한데 오답 판정 | 2 | 명백한 scorer/gold false negative 후보 |

두 workflow가 모두 실패한 직접 조회형 사례는 27개였다. 반복성이 확인된 실제
결함은 다음과 같다.

- catalog에 IBM이 존재해도 LLM이 IBM을 unresolved로 함께 반환하면 실행을
  중단했다. 서버가 catalog를 다시 대조하고 빈 계획을 한 번 재생성하도록
  수정했다. `F1-Q026` 재실행은 두 workflow 모두 정답으로 전환됐다.
- 검색 후보를 문맥 확장하는 과정에서 RRF 순위를 `set`과 행 번호 정렬로
  잃어버려, 상위의 `Total Revenue`보다 먼저 더 좁은 `Revenue`가 Reader에
  노출되는 결함이 있었다. 후보 순서를 보존하도록 수정하고 회귀시험을
  추가했다. 다만 질문이 단순 `매출`이라면 `Revenue`가 올바르며, 명시적으로
  `총매출`을 물을 때만 `Total Revenue`로 canonicalize한다.
- 미래 추정 질문을 실제 재무제표로 보내 전망 열을 놓쳤다. 전망·추정·outlook
  질문은 해당 시트가 catalog에 있을 때 `Key_Stats`를 우선하도록 수정했다.
- Reader가 비교·계산의 일부 값만 답하거나 근거 ID를 일부만 선택했다. 질문의
  기업·지표·기간을 먼저 점검하고 모든 피연산 셀을 인용하는 완전성 규칙을
  추가했다.

## 4. 이미 확인된 개선 효과

기준선 실패 중심 post-hoc 중에서도 `기업 명시 + catalog 존재 + 직접 원본 셀
gold` 조건을 만족하는 동일 56 run만 다시 비교하면 다음과 같다.

| 동일 난이도 subset | 정답 | 정확도 |
| --- | ---: | ---: |
| 개선 전 | 22/56 | 39.29% |
| 개선 후 | 35/56 | 62.50% |

이는 검색 근거 도달률뿐 아니라 실제 답변 정확도가 **+23.21%p** 개선된 결과다.
다만 실패 중심으로 고른 post-hoc subset이므로 전체 품질의 최종값으로 쓰지
않는다.

기존 105문항 직접 조회 세트를 두 workflow로 재실행한 회귀검사에서는 Answer가
138/210(65.71%)에서 145/210(69.05%)로 증가했고 실행 오류는 24건에서 0건으로
감소했다. 그러나 이 세트는 이후 전수검사에서 발견된 질문/FEATURE 의미
불일치를 아직 포함하므로 **실행 안정성 개선 증거**로만 사용하고 최종 RAG
정확도로 사용하지 않는다.

## 5. 최종 재평가 원칙

최종 보고값은 다음 조건의 새 동결 평가셋으로 산출한다.

1. 각 질문에 기업 또는 명시적인 대화 문맥을 포함한다.
2. 질문 용어와 실제 workbook FEATURE를 일치시킨다. `매출`과 `총매출`,
   `총부채`와 `총차입금`을 서로 다른 지표로 채점한다.
3. catalog 밖 기업은 abstention 평가로 분리한다.
4. 직접 조회와 계산·판단을 별도 지표로 보고한다.
5. 질문이 요구한 최종값만 필수 gold로 두고, 피연산자·설명값은 보조 gold로 둔다.
6. 동일 지표의 유효 대체 시트는 허용하되 Sheet exact는 별도 진단값으로 남긴다.
7. 기존 기준선과 post-hoc은 삭제하지 않고 새 결과와 나란히 제시한다.
8. 새 코드로 정제된 직접 조회형의 공식 수치는 새 124 run 결과만 사용한다.

## 6. 재평가 준비 상태

- 전체 209문항 중 93문항의 질문 또는 기업 범위를 수정했다. 현재 프로젝트
  범위에 포함하는 문항은 204건이며, 미적재 시트·기업 5건은 제외한다.
- 포함 문항 중 원본 셀 직접 조회형 124문항을 `rag_query` 단일 workflow,
  cache off 124 run으로
  `../04_benchmark_requests/benchmark-request-corrected-direct-124.json`으로
  동결했다. 124는 수정 문항 수가 아니라 포함 204건 중 자동 직접 셀 채점이
  가능한 subset 수다. 나머지 포함 80문항은 별도 formula/qualitative scorer가
  필요한 파생·판단형이다. BI는 동일 질문을 중복 실행하지 않고 metric catalog,
  exact evidence, snapshot 회귀시험으로 분리한다.
- 수정본 209개 전체 질문은 `evaluation-set-quality-review.md`, 기계 판독본은
  `../04_benchmark_requests/benchmark-questions-corrected.json`에 있다.
- 의미 보정·순위 보존·명시적 metric 및 source sheet 보존·Reader 근거 선택 복구는
  관련 단위·회귀 시험과 Ruff를 통과했다. 전체 백엔드 시험은 379 passed,
  2 skipped이며 Kubernetes 8080 환경에
  `38a18ed2c1bb-dirty-5a5d1f46011f` 이미지로 재배포했다.
- 사용자 승인 후 정제 직접 조회 124문항을 9개 샤드로 제출해 124/124 완료했다.
  Answer는 94/124(75.81%), 실행 오류는 0건, 총 추정비용은 $0.287985였다.
  상세 결과와 실패 분류는 `corrected-direct-rag-query-report.md`에 보존했다.
