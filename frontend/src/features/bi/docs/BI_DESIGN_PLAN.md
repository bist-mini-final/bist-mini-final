# BI 디자인 구현 계획서

## 1. 문서 역할

이 문서는 BI 페이지의 화면 구조, 카드 시스템, 차트, 배치 편집, 반응형 동작을 구현하기 위한 기준 문서다. 실제 지표 정의는 [BI_CONTENT_PLAN.md](./BI_CONTENT_PLAN.md), 백엔드 응답과 화면의 연결 방식은 [BI_INTEGRATION_PLAN.md](./BI_INTEGRATION_PLAN.md)를 따른다.

- 구현 순서: 1순위
- 구현 범위: `frontend/src/features/bi/`
- 주요 사용자: 재무 전문가가 아닌 일반 사용자
- 기본 화면 단위: 한 기업의 대시보드
- 제외 범위: 기업 간 비교, 고급 재무 분석, 별도 데이터 검수 화면

구현을 시작하기 전에 [BI_INTEGRATION_PLAN.md](./BI_INTEGRATION_PLAN.md)의 공통 데이터 계약을 확정하고, 그 계약과 같은 fixture를 만든다. 이 단계는 백엔드 구현이 아니라 디자인 재작업을 막기 위한 계약 고정 단계다.

## 2. 확정된 디자인 방향

디자인 해석은 다음과 같다.

> 기존 RAG Flow 작업 공간 안에서 동작하는 일반 사용자용 기업 재무 대시보드다. 기존의 밝은 녹색 계열, 부드러운 카드, 한국어 UI를 유지하고 정보 밀도는 중간, 모션은 상태 피드백 중심으로 제한한다.

다음 원칙을 고정한다.

- 기업은 탭으로 전환하며 한 화면에 한 기업만 표시한다.
- 최초 카드 수는 5개다.
- 모든 기업에 같은 카드 구성과 같은 배치 설정을 적용한다.
- 카드의 순서와 크기는 배치 편집 모드에서 드래그 및 리사이즈로 조정한다.
- 데이터가 없는 카드는 사라지지 않고 원래 위치에서 상태를 표시한다.
- 사용자가 숨긴 카드만 카드 목록에서 다시 추가할 수 있다.
- 화면은 설명이 필요한 전문 용어보다 핵심 수치, 쉬운 라벨, 짧은 도움말을 우선한다.

## 3. 현재 코드 기준선

2026-08-18 현재 확인한 구현 기준선은 다음과 같다.

- `/bi`는 `frontend/src/features/bi/BiPage.tsx`의 플레이스홀더다.
- 라우트 기준 파일은 `frontend/src/app/routes.ts`이며 BI 상태는 `planned`다.
- 공통 App Shell의 세로 스크롤 소유자는 `.product-page`다.
- 공통 색상, 글꼴, 포커스 스타일은 `frontend/src/styles/global.css`에 있다.
- 전역 App Shell 스타일은 `frontend/src/styles/app.css`에 있다.
- 프로젝트에 `DESIGN.md`가 없다.
- 현재 의존성에는 차트와 드래그 리사이즈 그리드 라이브러리가 없다.
- 기존 아이콘 계열은 `lucide-react`이므로 BI에서도 같은 계열만 사용한다.

BI 구현은 App Shell을 새로 만들지 않는다. `BiPage` 내부에서만 화면을 구성하고, 구현 완료 후 `routes.ts`의 BI 상태를 `ready`로 변경한다.

## 4. 디자인 시스템 선행 작업

UI 코드를 작성하기 전에 `frontend/DESIGN.md`를 만든다. 새 디자인을 발명하는 문서가 아니라 현재 `global.css`, `app.css`, `playground.css`, 공유 컴포넌트에서 반복되는 패턴을 추출하는 문서다.

`DESIGN.md`에는 최소한 다음을 기록한다.

1. 분위기와 정체성
2. 색상 토큰과 상태 색상
3. 한국어 UI 글꼴 및 숫자 타이포그래피
4. 간격, 최대 콘텐츠 폭, 카드 그리드
5. 탭, 버튼, 카드 셸, 툴팁, 상태 메시지의 구조와 상태
6. 드래그, 리사이즈, 탭 전환의 모션과 `prefers-reduced-motion` 처리
7. 카드 표면, 테두리, 그림자 전략
8. WCAG 2.2 AA 목표와 허용된 접근성 부채

BI에서 새 토큰이 필요하면 먼저 `DESIGN.md`에 역할을 기록한 뒤 CSS 변수로 추가한다. 기존 화면 전체를 BI 작업과 함께 재설계하지 않는다.

## 5. 라이브러리 결정 게이트

구현 시작 시 `frontend/package.json`과 각 라이브러리의 공식 문서를 다시 확인한다.

- 기본 그리드 후보: `react-grid-layout`
- 기본 차트 후보: `recharts`
- API 경계 검증 후보: `zod`
- 프론트 단위 테스트가 필요한 경우: `vitest`

선택 조건은 React 18, TypeScript 5.7, Vite 6 호환성, 키보드 대체 조작 가능성, 번들 크기, 유지보수 상태다. 호환되지 않으면 동등한 유지보수 라이브러리를 선택하고 이유를 `frontend/DESIGN.md`에 기록한다. 차트나 리사이즈 동작을 임의의 SVG와 포인터 계산으로 새로 만들지 않는다.

## 6. 페이지 정보 구조

페이지의 세로 순서는 다음과 같다.

1. 페이지 제목과 현재 스냅샷 상태
2. 기업 탭
3. 기간 선택과 배치 편집 도구
4. 5개 카드가 들어가는 대시보드 그리드
5. 필요한 경우에만 표시하는 페이지 수준 상태 메시지

### 6.1 상단 영역

- 제목: `기업 BI`
- 보조 정보: 현재 선택 기업, 기준 기간, 데이터 갱신 시각
- 갱신 중이면 기존 대시보드를 유지한 채 `새 데이터 처리 중`을 비차단 상태로 표시한다.
- 기업이 없으면 업로드가 필요하다는 빈 상태를 표시하되, BI 페이지 안에 별도 업로드 폼을 만들지 않는다.

### 6.2 기업 탭

- `role="tablist"`, `role="tab"`, `aria-selected`를 사용한다.
- 좌우 방향키로 탭을 이동하고 Enter 또는 Space로 선택할 수 있어야 한다.
- 기업 수가 많아지면 한 줄 가로 스크롤을 허용하되 페이지 전체에는 가로 스크롤이 생기지 않아야 한다.
- 탭에는 기업명만 표시하며 비교 체크박스나 다중 선택을 넣지 않는다.

### 6.3 도구 영역

- 기간: `최근 3개`, `최근 5개`, `전체`
- 배치: `배치 편집`, 편집 중 `완료`, `카드 추가`, `기본 배치로 초기화`
- `초기화`는 즉시 실행하지 않고 확인 절차를 둔다.
- 기간 선택은 모든 카드에 공통 적용한다.

## 7. 카드 그리드와 크기 규칙

### 7.1 기본 그리드

데스크톱은 12열 그리드를 기준으로 한다.

| 크기 | 기본 너비 | 표시 내용 |
|---|---:|---|
| 소형 S | 4열 | 대표 수치와 상태만 표시, 차트 없음 |
| 중형 M | 6열 | 대표 수치와 최근 3-5개 기간 차트 |
| 대형 L | 12열 | 선택한 전체 기간, 범례, 상세 툴팁 |

초기 배치는 다음과 같다.

| 순서 | 카드 | 초기 크기 |
|---:|---|---|
| 1 | 매출 및 성장 | M |
| 2 | 수익성 | M |
| 3 | 현금흐름 | M |
| 4 | 재무 안정성 | M |
| 5 | 재무 규모 | L |

정확한 행 높이와 최소 크기는 선택한 그리드 라이브러리의 측정 방식에 맞춰 fixture로 검증한 뒤 `cardRegistry.ts`에 한 번만 정의한다.

### 7.2 배치 편집

- 평상시에는 카드를 드래그하거나 리사이즈할 수 없다.
- 편집 모드에서 카드 헤더의 전용 드래그 핸들과 모서리 리사이즈 핸들만 활성화한다.
- 편집 중인 카드에는 현재 크기 S/M/L을 표시한다.
- 포인터를 사용할 수 없는 사용자를 위해 카드 메뉴에 `위로`, `아래로`, `왼쪽으로`, `오른쪽으로`, `크기 변경` 대체 조작을 제공한다.
- 숨김은 삭제가 아니다. `카드 추가` 목록에서 복구할 수 있다.
- 잘못된 저장 배치나 등록되지 않은 카드 ID는 기본 배치로 안전하게 정규화한다.

### 7.3 반응형 규칙

- 1280px 이상: 12열, S/M/L 전체 지원
- 768-1279px: 8열로 재배치, 크기 의미는 유지하되 너비를 컨테이너에 맞춘다.
- 768px 미만: 한 열로 재배치한다. 세로 순서 변경은 지원하지만 포인터 리사이즈 핸들은 숨기고 카드 메뉴의 S/M/L 선택을 사용한다.
- 375px에서 페이지 전체의 가로 스크롤이 없어야 한다.
- 카드 내부 차트는 컨테이너 너비에 반응하고, `전체` 기간은 축 라벨을 솎아서 표시한다. 차트 때문에 페이지가 가로로 스크롤되지 않게 한다.
- App Shell의 `.product-page`만 주 세로 스크롤을 소유한다. 카드 내부에 세로 스크롤을 만들지 않는다.

## 8. 공통 카드 구조

모든 카드는 `BiCardShell`을 사용한다.

1. 카드 제목과 쉬운 한 줄 설명
2. 대표 수치 영역
3. 차트 또는 소형 요약 영역
4. 상태, 단위, 기준 기간
5. 근거 보기와 챗봇 질문 액션
6. 편집 모드 전용 핸들 및 카드 메뉴

대표 수치는 LTM이 있으면 LTM, 없으면 가장 최근 FY를 사용한다. LTM과 FY0이 같은 값을 가리키면 차트에 같은 막대를 중복 표시하지 않는다.

표시 규칙은 다음과 같다.

- 값이 없으면 `0` 대신 `데이터 없음`을 표시한다.
- `NA`, `NM`, `null`은 의미를 보존한다.
- 추출이 모호하면 `확인 필요`를 표시한다.
- 금액은 원본 단위와 통화를 유지하고 카드 상단에 한 번만 표시한다.
- 퍼센트와 금액을 하나의 축에 섞지 않는다.
- 초록색과 빨간색을 단순한 증가 및 감소 의미로 기본 사용하지 않는다.

## 9. 카드별 차트 명세

### 9.1 매출 및 성장

- 핵심 수치: 매출, 전년 대비 성장률
- 차트: 기간별 매출 세로 막대
- 성장률: 별도의 작은 지표 또는 보조 영역
- 금액과 성장률을 이중 축으로 합치지 않는다.

### 9.2 수익성

- 핵심 수치: 영업이익, 영업이익률, 순이익, 순이익률
- 차트 기본: 영업이익과 순이익 그룹 막대
- 토글: `금액`, `이익률`
- 이익률 모드에서는 영업이익률과 순이익률만 표시한다.

### 9.3 현금흐름

- 핵심 수치: 영업현금흐름, CapEx, FCF
- 차트: 0선을 기준으로 영업현금흐름, 부호가 반영된 CapEx, FCF 막대
- CapEx가 유출이면 0선 아래에 표시한다.

### 9.4 재무 안정성

- 핵심 수치: 현금 및 단기투자자산, 총차입금, 순차입금
- 차트: 현금과 총차입금 그룹 막대, 순차입금 선
- 세 지표는 같은 금액 단위와 같은 축을 사용한다.

### 9.5 재무 규모

- 핵심 수치: 총자산, 총부채, 총자본
- 차트: 부채와 자본의 누적 막대, 총자산 값 라벨
- 100% 누적이 아니라 절대 금액을 표시한다.

## 10. 차트 공통 규칙

- 기간은 오래된 순서에서 최신 순서로 정렬한다.
- 금액 막대는 0 기준선을 사용한다.
- 결측값은 0이나 보간값으로 그리지 않고 간격으로 남긴다.
- 한 차트에는 하나의 단위만 사용한다.
- 3D 차트와 원형 차트는 사용하지 않는다.
- LTM은 FY와 구분되는 패턴, 테두리 또는 명시적 라벨을 사용한다.
- 툴팁에는 기간, 정확한 값, 단위, 필요한 경우 전년 대비 값, 근거 위치를 표시한다.
- 소형 카드는 차트를 렌더링하지 않는다.
- 중형은 최근 3-5개 기간, 대형은 사용자가 선택한 범위를 표시한다.

## 11. 화면 상태

### 11.1 페이지 수준

- 기업 없음
- 최초 데이터 처리 중
- 최신 스냅샷 준비 완료
- 일부 지표만 준비된 부분 완료
- 이전 스냅샷을 보여주면서 새 파일 처리 중
- 새 처리 실패 후 이전 스냅샷 유지
- 조회 실패

### 11.2 카드 수준

- loading: 실제 카드 구조와 같은 skeleton
- ready: 대표 값과 차트 표시
- missing: 카드 위치를 유지하고 `데이터 없음`
- ambiguous: `확인 필요`와 근거 보기 제공
- invalid: 계산 또는 단위 오류를 쉬운 문장으로 표시
- hidden: 사용자 설정에 의해 그리드에서만 제외

부분 완료에서는 준비된 카드만 정상 표시하고 나머지는 해당 상태를 카드 안에서 표시한다. V1에는 별도 검수 페이지를 추가하지 않는다.

## 12. 접근성과 모션

- WCAG 2.2 AA를 목표로 한다.
- 본문과 핵심 수치의 대비, 포커스 링, 상태 라벨을 색상 외 정보로도 구분한다.
- 모든 버튼의 터치 목표는 모바일에서 최소 44px을 확보한다.
- 탭, 기간 선택, 카드 메뉴, 배치 대체 조작은 키보드로 사용할 수 있어야 한다.
- 드래그와 리사이즈에는 화면 읽기 도구용 상태 안내를 제공한다.
- 모션은 탭 활성 표시, 카드 이동, 상태 전환 피드백에만 사용한다.
- 위치 이동은 spring 또는 짧은 transform, 색과 opacity는 100-200ms 범위로 제한한다.
- `prefers-reduced-motion: reduce`에서는 카드 이동 애니메이션을 제거하고 즉시 상태를 바꾼다.

## 14. 구현 순서

1. `frontend/DESIGN.md`에 현재 디자인 시스템과 BI 원칙을 기록한다.
2. [BI_INTEGRATION_PLAN.md](./BI_INTEGRATION_PLAN.md)의 응답 타입과 동일한 `dashboardFixture.ts`를 만든다.
3. 카드 셸, 버튼, 탭, 상태 메시지, 툴팁을 primitive showcase에서 먼저 검증한다.
4. 페이지 상단, 기업 탭, 기간 선택, 5개 기본 카드를 정적 fixture로 조립한다.
5. 차트 5종과 카드 S/M/L 표시 규칙을 구현한다.
6. 배치 편집, 드래그, 리사이즈, 숨김, 복구, 초기화를 구현한다.
7. 공통 localStorage 저장 규칙을 연결한다.
8. 접근성, 반응형, content stress를 검증한다.
9. 디자인 검증이 끝난 뒤에만 실제 API fixture를 제거한다.

## 15. 검증 시나리오

- 375px, 768px, 1280px에서 기업 탭과 5개 카드가 페이지 가로 스크롤 없이 보인다.
- 기업명이 매우 길어도 탭과 헤더가 깨지지 않는다.
- 카드 5개가 초기 배치로 표시되고 소형, 중형, 대형의 정보량 차이가 명확하다.
- 편집 모드 밖에서는 드래그와 리사이즈가 발생하지 않는다.
- 편집 후 새로고침해도 배치가 유지된다.
- 기업을 바꿔도 같은 배치가 적용된다.
- 잘못된 localStorage 값에서는 기본 배치로 복구된다.
- 데이터 없음, 확인 필요, 처리 중, 처리 실패 상태에서 카드 높이와 배치가 무너지지 않는다.
- 3개 미만 기간, 5개 미만 기간, LTM 포함, LTM 미포함 fixture를 모두 확인한다.
- 마우스 없이 기업 전환, 기간 전환, 카드 이동 대체 조작, 크기 변경을 수행할 수 있다.
- reduced motion 환경에서 이동 애니메이션이 제거된다.
- `npm run typecheck`와 `npm run build`가 성공한다.

## 16. 디자인 완료 조건

- 5개 기본 카드와 모든 S/M/L 상태가 fixture 데이터로 동작한다.
- 회사 탭은 단일 회사 선택만 지원한다.
- 공통 배치가 저장, 복원, 초기화된다.
- 빈 값과 모호한 값을 0으로 표시하지 않는다.
- 정해진 5개 차트가 단위 혼합 없이 렌더링된다.
- 모바일, 태블릿, 데스크톱 수동 QA와 키보드 QA를 통과한다.
- 디자인 단계에서는 실제 RAG 호출이나 외부 API 호출이 발생하지 않는다.
